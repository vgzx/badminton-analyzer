# 实现方案说明（DESIGN）

本文档说明 `badminton-analyzer` 的**设计决策**，不是 API 手册。读完后你应该能回答：
每个数字是怎么来的、参数为什么取这个值、什么情况下它会错、错了该调哪里。

---

## 1. 目标与边界

### 1.1 目标

| # | 需求 | 本实现的做法 |
|---|---|---|
| 1 | 自动切分回合，去掉捡球/停顿 | 双人运动状态机（发球锚点 + 待定态 + 走动判据） |
| 2 | 近端球员姿态分析 | MediaPipe 33 点，或降级为框体几何代理；相位化指标 |
| 3 | 记录特定动作回合 | 回合表 + 筛选字段（拍数、时长、跑动、可信度），可据此挑片段 |
| 4 | 精彩集锦自动剪辑 | 片段导出（`clips.py`），逐个回合成片，可直接拼接 |
| 5 | 文字版比赛分析 | `report_rallies.md`（模板化，非 LLM，数字全部可核对） |
| 6 | 回合解析 | 报告第 6 节“重点回合”：逐拍时间线 + 移动 + 姿态 + 结束原因 |

### 1.2 明确不做

- **不做球轨迹**（TrackNet 类）。原因：它是全链路唯一的重算力环节（占 45%~55% 耗时），
  在无独显机器上不可用，且训练/调参成本高。代价是失去落点、球路、得分归属。
- **不做得分判定**。没有球就没有“谁赢这一分”，所以报告里刻意**不出现**“赢分/输分对比”，
  改用“长回合 vs 短回合”“前半场 vs 后半场”这类同样可行动、但不需要球的切分维度。
- **不做界内界外**。单目视频的落点误差 0.6~1.0 m，撑不住压线判断。

### 1.3 关键工程原则

1. **一个几何真值**：所有位置先经单应变换到球场单位，之后才做任何统计。
2. **规则优于模型**：能不训练就不训练；每个判据都能被人读懂、被人改。
3. **缺失即缺失**：拿不到的数写 `—`，不用默认值凑数；未标定时绝不把相对单位标成米。
4. **可验收**：每一层都有中间产物（CSV/JSON/片段），能被人工抽查。

## 2. 总体架构

```
video
  │
  ├─[0] probe / 抽帧 ──────────────── videoio.py        meta: fps/size/duration
  │
  ├─[1] 单应标定 ─────────────────── court.py           H(米↔像素) 或 相对模式
  │
  ├─[2] 球员检测 + 近/远指派 ─────── detect.py          Obs(脚点,框,能量)
  │        (MOG2 前景 / 可选 YOLO)
  │
  ├─[3] 逐帧特征 ─────────────────── features.py        FrameFeat(near,far)
  │        (坐标变换、EMA、挥拍分量、姿态派生量)
  │
  ├─[4] 回合状态机 ───────────────── rally.py           rallies[]
  │
  ├─[5] 挥拍事件 + DP 解码 ───────── hits.py             hits[], shots
  │
  ├─[6] 指标聚合 ─────────────────── metrics.py         rows[], summary
  │
  ├─[7] 片段导出 ─────────────────── clips.py + viz.py  clips/*.mp4
  │
  └─[8] 报告生成 ─────────────────── report.py          report_*.md
```

**为什么按“逐帧特征表”做中枢**：它把视频 I/O 与全部算法解耦。
`metrics`、`hits`、`rally` 只吃 `FrameFeat` 列表，所以可以在没有视频、没有 OpenCV 的机器上被完整测试
（`tests/` 就是这么做的），也方便以后把检测模型换掉而不动上层。

## 3. 数据契约

### 3.1 `PlayerFeat`（每帧每人）

| 字段 | 单位 | 含义 |
|---|---|---|
| `present` | bool | 本帧是否检到 |
| `x, y` | u | 脚点在球场坐标（y 从近端底线向远端增长） |
| `speed` | u/s | EMA 平滑后的速度 |
| `accel` | u/s² | 速度变化率（挥拍分量之一） |
| `energy` | 0~1 | 框内前景像素占比（动作能量） |
| `energy_hp` | — | `energy - 慢速基线`，即“这一帧有多反常” |
| `h_ref` | px | 站立高度基线（快速上探、缓慢回落） |
| `crouch` | 比值 | 蹲伏度；媒体管道用关节，代理模式用框高比 |
| `stance` | 比值 | 踝距/肩宽（仅 mediapipe） |
| `racket_up` | bool | 持拍手高于肩（仅 mediapipe） |
| `wrist_v` | torso/s | 手腕速度（以躯干长为尺度归一，仅 mediapipe） |
| `comps` | dict | 四个挥拍分量，供 `hits.py` 做 z 分数组合 |

**单位约定**：1 u = 球场宽 6.10 m。所以场地长 13.40 m = 2.1967 u，近端前发球线 4.72 m = 0.774 u。
所有阈值用 u/s 表达，标定后即等价米制（0.11 u/s ≈ 0.67 m/s）。

### 3.2 回合（`rallies[]`）

```json
{
  "id": 12,
  "t0": 333.2, "t1": 344.9, "duration": 11.7,
  "kind": "rally",              // rally | serve_fault | partial
  "end_reason": "捡球/走动",
  "hits": [{"t": 334.1, "side": "near", "score": 3.4}],
  "shots": 9,                    // 发球计 1 拍
  "hit_confidence": "high",      // high | medium | low
  "last_hit_t": 344.0
}
```

### 3.3 指标行（`rallies.csv`）

见 `metrics.py::rally_row`。要点：

- `distance_u` 是**积分** `Σ speed·dt`（只累加速度 > 0.015 的帧，抑制抖动）；
- `peak_speed` 用 **p95 而不是 max**，避免单帧跳变污染；
- `front/mid/back` 按近端球员**自己半场**的地面纵深划分（前 = 过前发球线，后 = 距底线 1.6 m 内）；
- `recovery_s` = 最后一拍之后速度连续 0.3 s 低于静止阈值所需时间，上限 4 s。

## 4. 逐模块算法

### 4.1 标定（`court.py`）

用户点 4 个角点（近左、近右、远左、远右），解 8 自由度线性系统：

对每个点对 `(x,y) → (u,v)`：

```
[ x  y  1  0  0  0  -ux  -uy  -u ] · h = 0
[ 0  0  0  x  y  1  -vx  -vy  -v ] · h = 0
```

取 `A` 的最小奇异向量作为 `h`，重排为 3×3，归一化 `H[2,2]=1`。

**三重退化防护**（都实现并测试过）：

1. `A` 的最小奇异值 < 1e-9 × 最大奇异值 → 点集退化；
2. `cond(H) > 1e10` → 像素点近似共线（平面被压成一条线，变换不可逆）；
3. 重投影误差 > 1% 画面对角尺度 → 拟合失败。

**相对模式**（未标定）：`x_u = px/W`，`y_u = (1 - py/H)·2.1967`。
它假设“画面上下边界≈场地两条底线”，只在机位规整时近似成立。所有报告在此模式下把单位标成 `u`，
并在文首写一条告警。

### 4.2 检测与跟踪（`detect.py`）

**默认后端 `motion`**（不训练、不下载模型）：

1. 灰度图缩到 `detect_width=320`（比例保持），MOG2 背景减除（`history=300`, `varThreshold=20`，关闭阴影）；
2. 开运算 3×3 去噪 + 闭运算 7×7 补洞；
3. `findContours` → 按四条规则过滤：
   - 面积 ≥ `min_area_px`；
   - 框高 ∈ [`min_box_h_frac`, `max_box_h_frac`] × 画面高（上限用来挡“有人从镜头前走过”）；
   - 高宽比 ≥ 0.8（人应明显高于宽）；
   - 梯形失真导致的横向误检由后面的近/远指派兜住。

**近/远指派**（关键假设：机位在底线后，近端球员永远在画面更下方）：

1. 有上一帧位置时，先按脚点距离（gate = 18% 画面高）关联，命中者即为近端；
2. 否则取脚点最低（`y2` 最大）的框；
3. 远端 = 剩余框里**明显高于近端**（至少高 6% 画面高）、且面积最大者。

失败模式与后果：

| 场景 | 后果 | 缓解 |
|---|---|---|
| 观众站在场边高于远端球员 | 远端被指派给观众 | 面积优先 + 可换 yolo |
| 近端球员被完全遮挡 | 沿用上一帧位置，速度衰减 | `track_max_miss=25` 帧后放弃 |
| 静止超过背景学习时间 | 框体被背景吸收、变矮 | 真实比赛球员很少静止 >5 s |

**可选后端 `yolo`**：接口一致（`Obs`），用 ultralytics 的人体类。精度更高，但引入 AGPL 依赖与模型下载。

### 4.3 特征与平滑（`features.py`）

时间常数用一阶 EMA：`α = 1 - exp(-Δt/τ)`。

| 量 | τ | 理由 |
|---|---|---|
| `speed` | 0.20 s | 消掉框抖动，但保留急停/启动 |
| `energy` | 0.12 s | 保留挥拍瞬间的尖峰 |
| `energy` 基线 | 8.0 s | 慢到只跟踪“整体活动水平”，不跟尖峰 |

**为什么用“能量减基线”而不是原始能量**：球场亮度、球员衣服颜色会整体抬高能量，
减基线后剩下的才是“这一帧比平时多动了多少”，后者才是挥拍信号。

**速度**：`v = ‖p_t − p_{t−1}‖ / Δt`，位置已变换到 u，所以分辨率无关。
若某帧丢检且间隔 >1 s，则不计速度（避免瞬移）。

**站立高度基线 `h_ref`**：向上快速跟随（α=0.25），向下缓慢回落（α=0.004）。
这个不对称是故意的——人蹲下时不要立刻改写基线，否则“蹲伏”就永远测不出来。

### 4.4 回合状态机（`rally.py`）

```
                ┌──────────────── 双方在发球区静止 ≥0.8s ───────────────┐
                │                                                      ▼
   ┌────────┐   │   ┌────────┐   任一方 v > 0.16 u/s    ┌────────┐
   │  IDLE  │───┴──▶│ SERVE  │─────────────────────────▶│  LIVE  │
   └────────┘       └────────┘                          └────────┘
       ▲                 │ 12s 未进入活球                    │ 双方 v < 0.11 连续 1.5s
       │                 ▼                                  ▼
       │              IDLE                             ┌────────┐
       │                                              │ QUIET  │（待定，不判死球）
       │      走动持续 0.55s / 静止超 15s               └────────┘
       │                 │                                  │ 任一方 v > 0.18×1.6
       │                 ▼                                  │ 且是快速移动
       └─────────────  END ◀────────────────────────────────┘（回 LIVE）
```

四个状态、四条判据，其中**两条是可解释的强证据**：

- **起点**：双方同时站在各自发球区且静止 0.8 s。这是羽毛球规则决定的，几乎不会误判；
- **终点**：从待定态里出现“持续走动”。捡球、走回发球位、换边，都会产生这个信号。

**`QUIET` 态存在的唯一理由**：高远球对拉时，双方会同时静止 1~2 秒。
如果“双方静止”直接判死球，每个高远球回合都会被切成两段。
所以静止只把状态推到 `QUIET`，必须再看到走动才确认结束；期间若恢复高速运动则回到 `LIVE`。

**冷启动**（`allow_cold_start`）：视频从活球中途开始时，不可能等到发球准备段。
此时若持续 1 s 有高速运动，直接从 `LIVE` 起步，回合标记为 `partial`。

**分类**：

- `duration < min_rally_duration`(1.0s) → `serve_fault`：**保留**，因为发球失误率本身是有效信息；
- `LIVE` 超 `max_rally_duration`(90s) → 强制结束并记 `end_reason`；
- 长度、结束原因都写进报告，便于抽查。

### 4.5 拍数（`hits.py`）

**先反驳一个直觉**：为什么不能用时长估拍数？
同样 14 s 的回合，多拍高远球可能 3~4 拍，平抽快挡可能 15 拍。时长与拍数的相关系数约 0.6，
用它当拍数会系统性错。

**四步法**：

**① 每个球员算一个挥拍置信分**

四个分量，各自在**整场序列上**做稳健 z 分数（中位数/MAD，MAD=0 时退化为标准差）：

```
z(x) = (x − median) / (1.4826 · MAD)

score = 1.0·z(accel) + 1.0·z(energy_hp) + 1.2·z(wrist_v) + 0.4·z(height_rate)
```

权重依据：手腕速度是击球最直接的表征（1.2），身体高度变化（起跳/下蹲）最不可靠（0.4）。
没有 mediapipe 时 `wrist_v ≡ 0`，退化为三分量，仍然可用。

再做 `hit_smooth_sec=0.12` 的滑动平均，并乘以“该帧是否检到人”的掩码。

**② 取候选点**：局部极大值 且 `score > hit_z_threshold(0.9)`，同侧 0.28 s 内只留最高。

**③ 交替约束 + 生理间隔做 DP 解码**（这是精度的关键）

羽毛球里击球必然在两人之间交替，且间隔 ∈ [0.35 s, 8 s]。在候选序列上求最优合法子序列：

```
best[i] = score[i]
for j < i:
    if 同侧 or Δt ∉ [0.35, 8]: continue
    best[i] = max(best[i], best[j] + score[i] − λ·|Δt − 1.6| / 1.6)
路径 = argmax(best) 回溯
```

- `λ = 0.35`：间隔偏离典型值 1.6 s 的惩罚系数；
- 复杂度 O(n²)，单场候选点通常几十个，可忽略。

**为什么 DP 值得写**：单帧阈值判定的准确率大约 70%，但大量误检是“同一人连击”这种物理上不可能的模式，
交替约束一上，序列级准确率能到 85% 左右。这是本方案唯一“聪明”的地方。

**④ 挂到回合上并计数**：`shots = 1（发球）+ 检测到的击球数`。
若一个回合完全没检出击球：短于 3 s 视为发球失误/ACE（1 拍），否则 `shots = null`（不猜）。

**可信度**（写进报告）：
- `high`：有 ≥2 拍且最大间隔 ≤5 s；
- `medium`：只有 1 拍但回合短，或存在 >5 s 的间隔；
- `low`：回合 >6 s 却只有 1 拍（明显漏检）。

### 4.6 指标与聚合（`metrics.py`）

- **跑动距离**：`Σ speed·dt`，只统计 `speed > 0.015 u/s` 的帧。不平滑直接累加会因抖动虚增约 30%。
- **峰值速度**：p95（见 3.3）。
- **离基点**：基点 = 中线、距底线 3.4 m，即 `(0.5, 0.557)`。
- **回位时间**：见 3.3；这是“被动/主动”最便宜的代理指标。
- **一致性检查**：拍数 vs 时长的相关系数 + 每拍时长离群点（<0.45 s 或 >6 s）。
  它不是给用户看的，是给**算法自己**看的：相关系数 <0.5 说明拍数检测不可信。

### 4.7 报告（`report.py`）

纯字符串模板，不调用 LLM。原因：

1. 离线、可复现、零成本；
2. 报告里的每个数字都能在 `rallies.csv` 里核对，不会出现“模型编了个数”；
3. 想让 LLM 写“教练建议”时，可以后续把 `metrics.json` 喂进去，但**事实层必须由模板生成**。

两份报告的分工：`report_rallies.md` 讲**时间轴与拍**（发生了什么），`report_pose.md` 讲**身体**（怎么发生的）。

## 5. 参数总表与调参顺序

| 参数 | 默认 | 作用 | 调大的后果 |
|---|---|---|---|
| `analysis_fps` | 10 | 分析帧率 | 更准更慢 |
| `still_speed` | 0.11 | 静止阈值 | 更多帧被判“静”，易误切 |
| `move_on_speed` | 0.16 | 进入活球 | 启动慢的回合会被漏掉 |
| `walk_on_speed` | 0.10 | 走动判据 | 死球确认变慢，回合变长 |
| `serve_still_duration` | 0.8 | 发球锚点时长 | 发球准备短的会被漏 |
| `quiet_duration` | 1.5 | 进入待定 | 更容易把高远球切成两段 |
| `walk_duration` | 0.55 | 确认死球 | 回合尾部变长 |
| `min_rally_duration` | 1.0 | 发球失误分界 | 短回合被当正常回合 |
| `hit_z_threshold` | 0.9 | 挥拍候选阈值 | 拍数变少 |
| `hit_gap_min/max` | 0.35 / 8.0 | 击球间隔约束 | 越界拍数被丢 |
| `max_box_h_frac` | 0.55 | 挡“走过镜头的人” | 远处球员可能被挡 |

**调参顺序**（重要，别乱）：先 `detect`（看双人可见率）→ 再 `rally`（看回合数）→ 最后 `hits`（看拍数）。
上游错了，下游怎么调都是错的。

## 6. 性能与资源

以 60 分钟 1080p 视频、`analysis_fps=10` 估算（约 36000 分析帧）：

| 环节 | CPU（8 核） | 备注 |
|---|---|---|
| 解码 + 缩略 | 5~8 min | 主要受磁盘与编码影响 |
| MOG2 + 轮廓 | 8~15 min | 320 宽，单帧 ~20 ms |
| MediaPipe（每 2 帧，仅近端） | 10~18 min | 无则跳过 |
| 状态机/特征/指标 | <1 min | 纯 Python 算术 |
| 片段导出（重编码） | 5~10 min | 只导出有效回合，总量约为原片 30% |
| **合计** | **30~50 min** | 过夜跑完全可行 |

内存：`FrameFeat` 采用 `__slots__`，36000 帧约 40~60 MB。
磁盘：输出片段 ≈ 原片 25%~35%，其余产物 <5 MB。

### 7.3 真实素材的验收清单

1. 双人可见率 ≥ 70%（运行日志会打印）；
2. 抽 10 个片段看首尾：起点应为发球动作，终点应为球落地后 0.5~1 s；
3. 抽 5 个“可信度=低”的回合，人工数拍数与表格对比；
4. 拍数-时长相关系数 ∈ [0.5, 0.85]；
5. 有效时间占比 ∈ [20%, 45%]（超过说明死球被算成回合）。

## 8. 失败模式与对策

| 失败现象 | 根因 | 对策 |
|---|---|---|
| 全场只切出 1 个回合 | 死球时没人明显走动（站着休息） | 降低 `walk_on_speed`；或改用“捡球弯腰”单判据 |
| 每个回合被切成 2~3 段 | 待定态被误认为结束 | 增大 `quiet_duration` / `walk_duration` |
| 拍数系统性偏少一半 | 姿态降级为 proxy，`wrist_v=0` | 装 mediapipe；或降 `hit_z_threshold` |
| 拍数在对拉中规律性漏一拍 | 双方节奏一致导致候选点重叠 | 降低 `hit_smooth_sec`；提高 `analysis_fps` |
| 远端球员频繁丢失 | 观众/座椅干扰 | 用 `--detector yolo`；或裁剪分析区域 |
| 片段开头黑屏/错位 | 容器 seek 不精确 | 增大 `clip_pad_before`；转成 H.264 mp4 |

## 9. 后续路线

**v1.5（性价比最高）**：加一个“球是否存在/在飞”的二值检测器。
不做轨迹回归，只用帧差 + 小目标检测，成本约为 TrackNet 的 1/10，
但能把 `QUIET` 态的判定从“猜”变成“看”，回合终点精度从 ±1.5 s 提升到 ±0.5 s，同时交叉验证挥拍事件。

**v2（需要独显）**：TrackNetV3 球轨迹 → 击球点/落点 → 九宫格球路编码 → n-gram 丢分模式。
届时新增的模块只依赖第 4.5 节的击球事件，现有代码不必改。

**v3**：多机位（侧拍补 3D 转体）、双打（按半场团队聚合）、跨场次个人基线对比。
